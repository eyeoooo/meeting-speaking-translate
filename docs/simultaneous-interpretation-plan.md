# 双向同声传译方案

> 目标（用户 2026-07-30 定）：**我说中文，对方听到日语；对方说日语，我听到中文。**
> 三个必须正面回答的问题：**准确性、延迟、声音模拟。**
> 准确度参照系：Typeless（用户实测中文→日语最准的产品）。
>
> **用户裁定（2026-07-30）**：
> 1. 不向对方声明是 AI 同传。
> 2. 同传引擎用 **GPT-realtime**（OpenAI Realtime translations，speech-to-speech）——
>    用户判断为当前最好的方案。分句级联降为备选升级路径（见 §5）。

---

## 0. 一句话结论

**双向都走 OpenAI Realtime translations（gpt-realtime-translate）**：
收听方向（日→中）已经在线上跑；发言方向（中→日）是同一个协议类反向再开一路——
输入从"被控机声音"换成"耳麦麦克风"，输出从"本机播放"换成"Mac_Out 注入会议"，
语言从 zh 换成 ja。协议处理、重连、VAD 门控、转写事件的全部实现与实机经验
（含 `audio.input.transcription` 那个 mock 测不出的坑）直接复用，工程量是四个方案里最小的。

## 1. 为什么 Typeless 准——把它的配方拆开

Typeless 是听写产品，它的准确来自两件事，都与"快"相反：

1. **整句处理**：它等你说完一整句才出结果。ASR 拿到完整声学上下文，
   不需要对没说完的话下注。
2. **LLM 后处理**：转写结果再过一遍大模型做纠错、断句、术语统一。

这两件事映射到翻译上更加致命：中文是 SVO、日语是 SOV，**谓语在句尾**。
逐字流式翻译要么等（延迟等于没流式），要么猜（猜错就是事故）。
一句"我们不接受这个价格"，流式译到一半时"接受/不接受"还没出现——
这不是工程问题，是语序的数学问题。

所以配方是：**准确性来自"整句 + 上下文 + 术语表"，延迟用"三级流水线全流式衔接"去追回。**
两者不矛盾，分工不同。

## 3. 架构：两条方向、同一个协议类

```
【发言 中→日】（新增，复用 RealtimeInterpreter）
耳麦麦克风(系统默认输入, 48k→24k 重采样)
  → VAD 门控（静音不计费，现成机制）
  → Realtime translations 会话 B（input=zh, output.language=ja, 内置语音）
  → 日语音频 deltas → UplinkPlayer → Mac_Out → 被控机麦克风 → 会议
  → 同时 input_transcript（我的中文）+ output_transcript（日语译文）→ 面板第三泳道自查

【收听 日→中】（现有链路，不动）
被控机扬声器 → Mac_In → Realtime translations 会话 A（input=ja, output=zh）
  → 中文字幕（双泳道）；译文语音可选（默认关，字幕是可靠性锚点）
```

两条方向是**两个独立的 Realtime 会话**，互不影响、可并行工作；
任一方向断线只影响自己（epoch 重连机制现成）。参谋的"只读会议原文"边界原样适用。

## 4. 三个问题的正面回答

### 4.1 准确性

- **整句翻译，不逐字**（§1 的结论，不再重复）。
- **滚动双向上下文**：翻译 prompt 里带最近 N 句对话（对方的日语原文 + 我此前说过的话
  + 我方译文），指代、省略、话题连续性都有依据。这是单句翻译器（包括 Typeless
  的听写场景）没有的优势——我们手里有整场会议。
- **brief 术语表**：人名、产品名、数字敏感词在 brief.md 里给定日语读法与固定译法，
  prompt 强约束。参谋已经在用同一个文件，零新增配置面。
- **自见回显**：我的中文转写 + 日语译文实时显示在面板上（字幕第三泳道）。
  说错了、译错了，我自己第一个看见——一键静音（muteItem 复活）就是刹车。
- **敬语档位**：商务日语的丁寧語/敬語由 prompt 固定，不靠模型自由发挥。

### 4.2 延迟

预算（说完一句话之后）：

| 级 | 耗时 | 靠什么压 |
|---|---|---|
| 句尾判定 | 0.5–0.8s | VAD hangover；说话期间 ASR 已流式跑，句尾只等定稿 |
| 转写定稿 | 0.2–0.4s | 流式 ASR 增量早已算完大半 |
| LLM 翻译首 token | 0.4–0.9s | 小快模型（Haiku 级）+ prompt cache（上下文前缀稳定） |
| TTS 首音 | 0.3–0.5s | 流式 TTS，边生成边播 |
| **合计** | **1.5–2.5s** | 三级衔接全流式，无一级等上一级"全部完成" |

两个纪律性事实必须接受：
1. **1.5–2.5 秒是这个语序组合下"准确同传"的物理下限区间**。专业人类同传对
   日中也要拖 2–4 秒（等谓语）。把目标定在 1 秒以内等于把准确性押出去。
2. **说话方式是延迟的一半**：短句、句间停顿，延迟体感就好；一句 30 秒的长复合句，
   任何系统都只能等句尾。这是使用者可以自己控制的变量，面板上给出实时提示。

### 4.3 声音模拟

用户已裁定用 GPT-realtime，其语音为 **OpenAI 内置声线**（自然度高，但不是用户本人音色）。
配合"不向对方声明 AI 同传"的裁定，落地含义：

- 选一个与用户性别、年龄感匹配的内置日语声线并固定（不随版本漂移）。
- 真正的跨语言声线克隆（对方听到"你的声音在说日语"）在 Realtime 上做不到——
  OpenAI 不提供声线克隆。若将来实测发现"不是本人声音"成为实际问题，
  升级路径是 §5 的分句级联（ElevenLabs / GPT-SoVITS 克隆），管线出口不变。

## 5. 备选与升级路径

| 方案 | 判定 |
|---|---|
| **OpenAI Realtime translations 双向（已选定）** | 工程最小、协议经验现成、延迟 2-3s 实测过。局限：内置声线（无克隆）、术语控制弱于 LLM 级联。M1 排练模式就是它的实测考场 |
| 分句级联（ASR→LLM→TTS 克隆） | **升级路径**，非当前方案。当 Realtime 的术语准确性或声线在真实会议中被证明不够时启用：三级全流式 1.5-2.5s，可克隆声线、可挂 brief 术语表。管线出口（UplinkPlayer→Mac_Out）与 Realtime 方案完全相同，切换不动硬件层 |
| 逐字流式同传（token 级） | 中日语序问题无解，准确性天花板低于可接受线。否决 |
| 人肉打字 + TTS | 延迟 10s+，不是同传。否决 |

## 6. 实施分期（每期独立可验收）

- **M1 排练模式**（先行，零会议风险）：耳麦麦克风 → 中文转写 + 日语译文
  上面板显示，**不出声**。用来实测转写准确率、翻译质量、真实延迟分布。
  离线可用 WavReplayBus 回放中文测试语料回归。
- **M2 出声**：+ 固定声线日语 TTS → Mac_Out 注入会议。静音开关复活为
  「发言静音」。真实会议验收端到端延迟与对方听感。
- **M3 声音模拟**：接入声线克隆（ElevenLabs 起步），A/B 对比固定声线。
- **M4 收听方向补语音**（可选，默认关）：同一条分句级联反向跑，
  日→中也出语音。字幕永远保留——它是可靠性锚点。

前置硬件：Type-C 耳麦一副（用户已计划）。到位前 M1 可用任何 USB/蓝牙麦克风开发。

## 7. 成本量级（每小时会议，粗估）

- 流式 ASR：$0.2–0.6
- LLM 翻译（小快模型 + prompt cache，按每分钟 3–5 句）：$0.1–0.4
- TTS（克隆声线，按实际说话 15 分钟/小时）：$0.5–2
- 合计 **$1–3/小时**，与现有字幕通道（$2/小时）同量级。

## 8. 与"会议模块独立化"的关系

本方案天然服从用户 2026-07-30 的架构裁定：会议智能体是独立产品，KVM 只是
音源之一。发言管线的输出端同样抽象——今天是 Mac_Out（KVM 场景），
将来 Teams 跑在 Mac mini 本机时输出端换成虚拟麦克风（BlackHole 一类），
管线本体一行不改。设备一律跟随系统默认，不硬编码。
