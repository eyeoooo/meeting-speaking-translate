# 音频网关会议产品化计划（2026-07-29）

## 0. 现状基线（已验收）

- 物理链路双向贯通（2026-07-29 实测）：收音方向 被控机→Mac_In 电平校准完成；发言方向 Mac_Out→被控机→Zoom→远端手机 听到合成语音。
- 关键校准值：**系统输入增益 30**（55/89 削顶）、**USB 声卡输出音量 84**（出厂 53 过弱）、系统默认输出=Mac mini 扬声器（防系统音漏会）、麦克风 TCC 授权在 `com.apple.Terminal`。
- 代码：`run / verify(capture|tone|talkback|loopback) / summarize` 已部署 MACMINI `~/audio-gateway`（Python 3.12 venv）；Whisper/Claude 依赖未装、未实测。
- 教训入档：纯音会被 Zoom 噪声抑制整体消除，测试一律用语音样本。

## 1. 产品目标：什么叫"正常会议"

操作者通过 KVM 参加被控机上的远程会议，达到以下验收线：

| # | 验收项 | 量化标准 |
|---|---|---|
| A1 | 听会 | 会议声音清晰连续，端到端延迟 ≤150ms（本地模式 ≤70ms） |
| A2 | 发言 | 远端听感正常（无削顶/机器音），一键静音 ≤200ms 生效 |
| A3 | 时长 | 90 分钟会议全程无断流、无爆音、无人工干预 |
| A4 | 产物 | 会后自动得到 m4a 录音 + 带时间戳转写 + Markdown 纪要 |
| A5 | 字幕 | 原生 Live Captions 亚秒级原文字幕可用（日/英） |
| A6 | 故障 | 拔线/设备消失/增益漂移可被检测并给出明确告警，不静默失败 |
| A7 | 隔离 | 音频子系统零接触 CH9329/串口/HID 链路（纯旁路，审计可证） |

## 2. 架构决策点（需拍板）

### D1 操作者位置模式 —— 决定工程量的主决策

**模式 L（本地）**：操作者在 Mac mini 旁，有线耳麦直插 Mac mini。
- 听会 = `--monitor` 回放到耳机；发言 = 耳麦 mic → Mac_Out。
- 工程量：≈0（现有代码即可），Mac mini 无内置麦需配一个 USB/3.5mm 耳麦。

**模式 R（远程）**：操作者在 MacBook/浏览器端，经 KVM 控制台开会（与看被控机画面同一形态）。
- 需新建 浏览器 ↔ Mac mini 双向音频桥：
  - 下行：Mac_In → 网关进程 → WebSocket PCM（48k/16bit/mono，20ms 帧）→ 浏览器 AudioWorklet 播放（抖动缓冲 60–100ms）；
  - 上行：浏览器 getUserMedia（MacBook 麦）→ WebSocket → 网关 → Mac_Out；
  - 前端加"会议音频面板"：连接/断开、一键静音、双向电平表；
  - 延迟预算：Tailscale 内网 RTT ~10ms + 缓冲 ≈ 单向 100~150ms，A1 达标。
- 工程量：后端 WS 通道 + 前端面板 + 网关侧 WS 客户端，约 2~4 个工作日节奏。
- 注意：走已有 KVM backend 时仅复用 HTTP/WS 基础设施，**不触碰输入链路**（A7）。

**建议：L 先行（立刻能开会）→ R 跟进（真产品形态）**。L 的全部产出（校准、doctor、稳定性）都被 R 复用，无弃件。

### D2 发言麦克风来源

- 模式 L：外接有线耳麦（需采购/找现货，验收时确定设备名关键字）。
- 模式 R：浏览器 getUserMedia（MacBook 内置麦即可，无新增硬件）。
- iPhone 连续互通麦仅作应急，不进产品路径（连接态不稳定）。

## 3. 分阶段计划

### P0 基线固化（0.5 天）——任何模式都需要

1. **`doctor` 子命令**：一键体检——声卡在位/采样率 48k/输入增益=30/输出音量=84/默认输出=内置扬声器/麦克风 TCC 可用（采集 1s 判别数字零）/磁盘余量。任何一项不符给出修复命令或直接 `--fix` 自动纠正（osascript+SwitchAudioSource）。
2. 校准漂移防护：`run` 启动时自动跑 doctor，不达标 fail-closed 拒绝开会并打印原因。
3. 验收：故意改乱增益/默认输出后 `doctor --fix` 一键复原。

### P1 会议核心链路（模式 L：0.5 天 / 模式 R：+2~4 天）

- L1：耳麦到位 → `run --monitor <耳麦> --mic <耳麦>` 真实会议 30 分钟试运行（A1/A2 主观验收 + 静音切换实测）。
- R1：WS 音频桥后端（网关进程内加 `--bridge ws://` 模式）；R2：KVM 前端会议面板；R3：MacBook 端 30 分钟会议验收。
- 验收：A1 + A2。

### P2 可靠性与无人值守（1~2 天）

1. **设备异常处理**：CoreAudio 设备消失/流错误 → 立即停流 + 显式告警（不静默重试）；恢复后一键重启会话。
2. **会中电平哨兵**：持续 30s 全静音（-inf）→ 告警"线路/对端异常"；持续削顶 → 告警降源音量。
3. **长会烧机**：2 小时双向流 + 录音，观察双卡时钟漂移（监听队列 drop-oldest 已兜底，记录 xrun/drop 计数）。
4. 开机自启评估：LaunchAgent 跑 GUI 会话拿 mic TCC 需单独授权 python 或打包 .app——**一期不做自启，保持 Terminal 启动**（权限模型已验证），仅做"一条命令进入待会状态"。
5. 验收：A3 + A6。

### P3 AI 会议能力接入（1 天，代码已备）

1. Mac mini 装 `mlx-whisper` + 模型预热（large-v3-turbo ≈1.6GB）；配 `ANTHROPIC_API_KEY`。
2. Live Captions 开启与语言配置（日/英），书面操作卡。
3. 全流程演练：测试会议 → 会后自动 m4a/转写/纪要（A4/A5 验收）。
4. advisor 实测：真实 brief 一份，观察触发节奏与建议质量，调 interval/hotwords 默认值。

### P4 产品化收尾（0.5~1 天）

1. 文档三件套：会前 checklist（doctor 一键）、会中操作卡（静音/结束/故障应对）、故障速查表（本次排障经验全部沉淀：数字零=TCC、削顶=增益、纯音被 NS 吃、输出 53 过弱…）。
2. A7 隔离审计说明：音频子系统进程清单、无串口/HID 依赖声明。
3. 代码合入 KVM 主线（PR + review）。

## 3.5 架构修订（2026-07-30，UU 工作流适配）

实际操作席 = MacBook —UU远程→ Mac mini —KVM→ 被控机；KVM 页面只开在 UU 里的 Mac mini 桌面。
UU 能力边界（官方）：macOS 被控端支持声音下行；**麦克风直连仅支持 Windows 被控端**。据此 R 架构定稿：

- 听会：`bridge --monitor "Mac mini扬声器"` → UU 声音同步承载到操作席（零新界面）；
- 发言：MacBook 跑 `micagent`（一条命令，WS 上行到网关 → Mac_Out）；**必须戴耳机**（agent 无 AEC，扬声器外放会把会议声喂回麦克风形成回声）；
- 静音：网关服务端权威状态（WS/POST 均可切换，全端即时生效+广播）；
- 控制面：R2 = KVM 前端页面内嵌会议面板（连接状态/静音按钮/双向电平），直连网关 8787，不经 backend；bridge.html 降级为调试面板。

传输层已于 2026-07-30 全链路自检通过（MacBook→Tailscale→网关帧率正确、静音丢弃、状态广播、断线重连）。

## 4. 风险表

| 风险 | 影响 | 缓解 |
|---|---|---|
| 双卡独立时钟漂移（长会） | 监听欠/过载、录音与转写时间轴微偏 | P2 烧机量化；drop-oldest 兜底；必要时监听路加简易重采样 |
| 被控机 IT 策略重置 Zoom 设备选择 | 会议突然无声 | 会前 checklist 固定检查项；会中电平哨兵报警 |
| LaunchAgent/自启的 TCC 归属 | 自启后采集全零 | 一期不自启，Terminal 启动为唯一受支持入口 |
| Zoom 噪声抑制/自动增益干预 | 发言被削弱 | 发言链路保持真人语音电平（已验）；异常时指引关 Zoom NS |
| Mac mini 无内置麦（模式 L） | 无法发言 | 耳麦采购为 L1 前置项；R 模式无此问题 |
| 模式 R 的网络抖动 | 音频卡顿 | 抖动缓冲自适应 60~150ms；Tailscale 内网基线良好 |

## 5. 里程碑排序（建议）

```
P0 doctor 固化 ─▶ L1 本地模式首会 ─▶ P2 可靠性 ─▶ P3 AI 能力 ─▶ R1-R3 远程桥 ─▶ P4 收尾合入
     0.5d              0.5d             1~2d          1d            2~4d           1d
```

L 先行让"能正常开会"最快达成；R 桥是产品终态，放在可靠性和 AI 能力验证之后，避免在不稳的地基上叠网络层。
